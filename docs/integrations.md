## M4 Twitch (implemented 2026-10-31)

Verified against dev.twitch.tv docs on 2026-10-31. The code is in `server/twitch/`, and the setup guide is [twitch-setup.md](twitch-setup.md).

- **Auth:** authorization-code grant to `http://localhost:<PORT>/auth/callback`, with a random `state` (10 min, single use) and `force_verify`. Each login is checked with `GET https://id.twitch.tv/oauth2/validate`: the client ID must match and every requested scope must be granted. Tokens refresh five minutes before expiry or on a 401, and are revalidated hourly. Revoked tokens are dropped. Tokens live in `.artifacts/twitch/tokens.json` (mode 600, git-ignored) and never reach the browser.
- **Scopes:** broadcaster `user:read:chat user:write:chat channel:bot channel:read:redemptions channel:manage:redemptions`; optional bot `user:read:chat user:write:chat user:bot`. The bot must be a different account.
- **EventSub WebSocket** (`wss://eventsub.wss.twitch.tv/ws`): subscriptions use user tokens (app tokens fail on WebSockets). The bridge subscribes from `session_welcome`, inside the 10 s window. Silence longer than `keepalive_timeout_seconds` (+5 s) triggers a reconnect with backoff and fresh subscriptions. `session_reconnect` opens `reconnect_url` and keeps the old socket until the new welcome (subscriptions carry over). Notifications are de-duplicated by `message_id`, and revocations are surfaced in the panel. The client sends nothing except pongs.
- **Subscriptions:** `channel.chat.message` v1 `{broadcaster_user_id, user_id: reader}` on the reader's session (bot, or broadcaster without a bot). `channel.channel_points_custom_reward_redemption.add` v1 `{broadcaster_user_id, reward_id}` runs on the broadcaster's session. One session per token user keeps within the 3-connection limit.
- **Helix:** `POST /chat/messages` (500-char cap; `is_sent=false` is reported; replies are throttled to about 1/s with a 20-message buffer). `GET /users` (`broadcaster_type` gates rewards). `GET /channel_points/custom_rewards?only_manageable_rewards=true`, then `POST` to create the reward once. `PATCH /channel_points/custom_rewards/redemptions` sets `FULFILLED` or `CANCELED` (refund). Only allowed while UNFULFILLED, and only by the app's own Client-Id.
- **Trust:** viewer text from chat and redemptions goes through the same `ViewerRequestSchema`, per-viewer cooldown, capacity limit and local approval (unless `AUTO_APPROVE=true`) as local requests. It is always data, never agent instructions. Shared-chat messages from other channels are ignored.
- **Not yet:** API moderation (M5), and redemptions left unresolved by a crash (they stay UNFULFILLED in the Twitch queue, where the streamer can refund them manually).
